# Sift：多源内容提炼工作流

## 定位与 90 秒介绍

Sift 是把视频字幕、文件和长文本转换成可回查原文的结构化摘要工具。我用它探索 AI 应用的工程化，而不是实现通用自主 Agent。

用户选择来源与摘要深度后，系统先获取正文，再保留段落、PDF 页码或字幕时间标记。短文直接提炼，长文分块提炼后合并。输出不仅要通过结构校验，每条引文还必须匹配对应原文位置；不合格时只允许修复一次，持续失败就明确报错。最终展示重点、数据、决定、行动、风险与引用上下文，并支持 Markdown 导出。

最重要的工程取舍是：流程由程序控制，不把下一步交给模型自由决定；给调用设定时间与次数预算；区分“JSON 合法”“引文真实”“结论正确”这三件不同的事。

我对合成文本、实际生成的 PDF/Word、合成字幕及长文本做了小规模验证；不把有限用例通过包装成生产准确率，也不承诺任意 YouTube 视频都能解析。

## 代码如何串起来

| 层 | 代码 | 责任 |
| --- | --- | --- |
| 输入与反馈 | `public/app.js`、`public/pdf-parser.js` | 浏览器 PDF 解析、请求状态、引用展开、导出、防止跨标签并发覆盖结果 |
| HTTP 边界 | `server.js` | 参数、上传与限流；统一错误码；传递取消信号与云端截止时间 |
| 来源适配 | `lib/file.js`、`lib/youtube.js`、`lib/supadata.js` | 文件正文、字幕获取、可选转写；不负责摘要推理 |
| 来源索引 | `lib/source.js` | 创建来源单元、保持原始定位、分块、校验引用与合并证据 |
| 模型工作流 | `lib/summarize.js` | Provider 适配、结构验证、有限修复、分块提炼/合并、调用记录 |

主路径：输入 → 解析 → 来源单元 → 分块提炼 → 校验/有限修复 → 必要时合并 → 再校验 → 展示与导出。

## 五个可以展开讲的技术点

### 1. 为什么不直接把全文扔给模型

长内容会增加 token 消耗、遗漏重点和超时风险。默认按约 12000 字符分块，尽量沿句子边界切分。字符数只是轻量预算，并不是精准 token 计数。每块带原始定位，不能重新从“段落 1”编号。

提炼输出是统一结构，合并时只允许复用分段输出已有的证据。合并输入按约 24000 字符预算分组；无法收敛时停止，不无限递归。最终最多展示的条数受简洁/标准/深度模式控制。

代价是多次调用、延迟增加以及合并仍可能丢失信息。本实现顺序调用，优先限制复杂度和瞬时负载，没有宣称解决所有跨段推理问题。

### 2. 为什么 JSON Schema 不足以保证摘要可信

Schema 能检查字段、类型、数量，无法证明“预算 99 万元”是真的。Sift 在运行时另查：quote 是否出现在同一 locator 和 seconds 的来源单元中。匹配采用 Unicode NFC 和空白归一化，不接受语义近似引用。

例如来源写“预算为 12 万元”，输出引用“预算为 99 万元”，即使 JSON 合法也会失败。反馈传给模型修复一次；仍失败不展示伪造结果。

但如果引用是真实的，模型却写了不受引用支持的结论，当前检查未必能发现。`semanticVerified: false` 明确表示没有完成语义事实验证。不能在简历写“杜绝幻觉”。

### 3. 如何控制错误、成本与取消

只针对结构/引用失败修复一次，不对认证失败、限流、拒绝、输出截断进行无差别重试。单次模型请求最多 25 秒，工作流还有总时限和默认 32 次调用上限；总时限到达后不会开始后续调用。

真实 token 来自服务 usage 字段，缺失则为 null；不编造价格或成本。修复失败那次调用也记录在 trace 中。浏览器断开会向摘要调用和 Supadata 传递取消信号；本地直连下载及实验性视觉识别没有覆盖同样完整的取消链。

所有摘要入口共用实例内 IP 限流，不能通过切换文本/文件入口绕开。但这不是商业产品级防刷：还没有账户、共享配额、分布式限流和租户隔离。

### 4. 为什么线上 YouTube 比文本难

浏览器能访问 YouTube，不代表 Vercel 出口 IP 能读取字幕。线上优先使用配置好的 Supadata，原生字幕不可用时可申请转写。Vercel 下读取/转写总预算最多 25 秒，应用为整个请求设置 50 秒截止时间，摘要使用剩余预算。

云端 Supadata 失败时不再启动不可控的直连备用链；把错误说明白。长转写需要排队，可能超出函数时限，此时应上传字幕或重试，不把失败当作摘要模型失败。本轮没有调用付费转写，也没有重新验证真实线上视频。

长期商业部署可考虑异步任务队列和任务查询，但当前面试版本未实现。视觉 OCR 属实验性选项，需明确配置服务支持的视觉模型，普通摘要 Key 不代表能用视觉识别。

### 5. 为什么没有 LangChain、RAG 或复杂 Agent 循环

该任务的流程已知：读取、提炼、校验、合并。让模型自主挑工具和反复探索，不一定增加效果，却会增加不确定性。有限修复不是 ReAct 自主循环。

Sift 没有知识库、embedding、向量检索与检索增强问答，所以不能说成 RAG 系统。直接实现少量 Provider 适配和工作流，比为了框架名称引入抽象更容易讲清和测试。

项目组合可以这样区分：ReproLens 展示受控浏览器执行与复现验证；Sift 展示多源 AI 工作流与可靠性控制；TraceBase 的 RAG 能力应按其实际实现另讲，不能把三个项目统称自主 Agent。

## 3 分钟演示顺序

1. 本地启动 Sift，粘贴 `scripts/fixtures.mjs` 中的合成试点内容，选择标准摘要。
2. 指出 12 万元、30 人、验收前不得上线，展开一条引用及上下文。
3. 展开处理记录，解释模型、提示版本、调用数与 token。健康状态“已配置”只表示有 Key，不表示刚通过实时鉴权。
4. 上传可提取文本的 PDF，展示页码；展示 Word 输入或 Markdown 导出任选其一。
5. 打开 `docs/evidence/model-evaluation.json` 的长文案例，展示 3 块提炼 + 1 次合并及首次失败后的有限修复记录。

没有可用网络或模型额度时，用验证报告讲解；不要把 UI 自动化的模拟后端冒充实时模型成功。演示避免私人文件及不可控长视频。

## 面试官可能追问

**是不是模型套壳？** 模型负责提炼，但来源解析、定位不变性、校验、调用预算、错误处理、UI 状态和验证都是应用层工作。也承认不是模型训练项目。

**怎么证明提升？** 先证明可测行为：错误定位被拒绝，引用修复有上限，长文合并不新增证据。本次只有小规模合成检查，没有 A/B 基线，不能声称提升了某个准确率百分点。

**引用都对，为什么结论还会错？** 引用存在性与语义支持不同，概括可能错误推断。需要更丰富人工标注与蕴含/事实检查评测；当前保留用户回查入口。

**为什么行动截止时间可能为 null？** 原文没有明确关联该行动的截止日期时应留空，不能把整项试点截止日期擅自套给每一个行动。

**如何防提示注入？** 来源作为不可信数据放进用户内容，系统提示要求不执行其中指令，输出结构和引用再校验。但这是缓解措施，未形成完整对抗评测，不能保证防住所有注入。

**PDF 扫描件怎么办？** 当前没有通用 OCR；文本提取为空时明确失败。Word 用正文段落定位，不伪造 Word 页码。

**150000 字符一定能成功吗？** 这是输入上限，不是成功承诺。剩余时限、调用预算与服务状态都会限制可处理内容，超限要减少内容，而不是无限重试。

**高并发怎么办？** 当前实例内缓存和限流，暂无任务队列、跨实例幂等和共享配额；不应称为成熟 SaaS。

## 简历描述建议

独立实现多源内容提炼工具 Sift，支持 YouTube 字幕、PDF/Word 与长文本输入；设计来源定位保留、分块提炼与合并、结构及引文匹配校验和有限修复机制，提供实际调用/token 记录与 Markdown 导出；通过自动化测试及小规模合成模型验证检查解析、溯源和异常路径。

避免写“生产级百万并发”“100% 准确”“通用 Agent”“完整 OCR”“所有 YouTube 都可解析”。讲清实际代码与限制，比新增框架名称更重要。
